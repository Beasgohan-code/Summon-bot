# Summon-bot

Summon-bot is a Telegram character-collection bot with a SQLite-backed economy, collections, market, auctions, moderation, streaks, achievements, and inline search.

## Production persistence

The bot now supports two runtime modes. With no `DATABASE_URL`, it uses the local SQLite file configured by `SQLITE_DB_PATH` and remains convenient for development. With `DATABASE_URL=postgresql://...`, every runtime database connection is routed through PostgreSQL. This is the recommended production mode because the database is external to the bot process and survives application restarts, redeployments, and ephemeral filesystems.

The repository includes `migrate_sqlite_to_postgres.py`. It creates the repaired schema, copies the existing SQLite data without modifying the source file, and resets PostgreSQL sequences. Always back up `summon.db` before migrating and verify row counts before switching the bot over.

```bash
cp summon.db summon.db.backup
export DATABASE_URL='postgresql://USER:PASSWORD@HOST:5432/summon_bot'
python3 migrate_sqlite_to_postgres.py --source summon.db
python3 smoke_test.py
```

## Configuration

Copy `.env.example` to `.env` and provide the Telegram credentials, owner ID, owner-panel password, and production database URL. Do not commit `.env`, database files, session files, logs, or generated bytecode. `BOT_TOKEN` and `OWNER_PANEL_PASSWORD` are deliberately not stored in source code.

## Health, keep-alive, watchdog, and Mini App

The bot starts a lightweight HTTP server on `0.0.0.0:$PORT` for the PTB webhook, `/healthz` liveness, `/readyz` database readiness, and the same-origin Mini App at `/app/`. Set `WEBHOOK_URL` and a random `WEBHOOK_SECRET`; Telegram updates are accepted only at the configured HTTPS webhook path. The Mini App authenticates every API request with Telegram WebApp init data and credits server-generated rewards to the existing bot balance.

`KeepAlive` requests the configured `KEEPALIVE_URL/healthz` at a safe interval so providers such as Render do not unnecessarily sleep the service. `Watchdog` performs a read-only PostgreSQL probe and records heartbeat/database state in the health response. Neither component changes the bot's command routing or economy rules.

Set `LOGGER_ID` to a Telegram channel or group where the bot can post. Warnings and errors are batched by a background worker, chunked safely under Telegram's message limit, and delivered without blocking command handlers. `LOG_TELEGRAM_LEVEL=WARNING` keeps routine logs out of the channel; use `INFO` only when diagnosing a deployment.

The Mini App assets are split into semantic HTML, responsive CSS, and a browser JavaScript module under `webapp/`. It includes dashboard balance, collection progress, secure daily/spin rewards, recent activity, leaderboard, theme switching, and Telegram haptics.

## Admin character upload

The owner and delegated sudo admins can upload a character by replying to a
Telegram photo, video, or GIF with:

```text
/upload Yelan Genshin-impact 5
```

The same command can be used as a caption on the media. The bot stores a
Telegram file reference in PostgreSQL rather than writing an upload directory
or exposing a bot-token URL. `/addchar` and `/add` remain available for
approved Catbox or ImgBB HTTPS URLs.

## Running reliably

Use `supervisor.py` under a service manager. Its default behavior is to restart the bot after an unexpected crash and to start it again after a machine reboot when used with `summon-bot.service.example`. This is safer than killing the bot every 10 or 15 minutes because forced restarts create avoidable downtime and can interrupt an in-flight transaction.

If a provider has a demonstrated memory leak and periodic recycling is genuinely required, set `AUTO_RESTART_MINUTES=10` or `AUTO_RESTART_MINUTES=15`. Leave it at `0` otherwise. The supervisor waits briefly between restarts to avoid a tight crash loop.

The service template assumes the project is installed at `/opt/Summon-bot`:

```bash
sudo cp summon-bot.service.example /etc/systemd/system/summon-bot.service
sudo systemctl daemon-reload
sudo systemctl enable --now summon-bot
sudo systemctl status summon-bot
journalctl -u summon-bot -f
```

## PostgreSQL versus MongoDB

PostgreSQL is the better primary backend for the current codebase because the bot already models users, collections, balances, inventories, auctions, market transactions, and relationships using SQL queries, constraints, conflict handling, and joins. MongoDB is technically possible, and `MONGO_URI` and `MONGO_DB_NAME` are reserved in `.env.example`, but it should not be added as a second write path casually. A complete MongoDB implementation would require a separate document repository, query redesign, transaction review, indexes, and a new migration/rollback plan. Running PostgreSQL and MongoDB as dual primaries would increase the risk of balance and inventory divergence.

## Validation

The repository includes `smoke_test.py`, which parses all Python modules, tests fresh database initialization, checks required tables, verifies key SQLite-to-PostgreSQL SQL translations, and imports the main command modules without starting Telegram polling.

```bash
python3 -m compileall -q .
python3 smoke_test.py
python3 check_schema.py
```

The bot cannot be started successfully until `BOT_TOKEN`, `OWNER_ID`, and `OWNER_PANEL_PASSWORD` are set in the environment.
